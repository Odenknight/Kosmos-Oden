# Engine pin, renderer close-ups and efficiency — 0.8.4

Kosmos 0.8.4 consumes GKOS-Engine 2.2.0 development source
`7511233717cd5ab9ce8f6cec76e9623a21e3c728` (Engine `main`, 2026-10-12).
Package declaration, Git lock resolution, script allowance, lock guard and
adapter fixture agree on that commit. The previous pin was
`777ba170b905952817e364f125c794152f118fa4`
([qualification](2026-09-13-engine-777ba17.md)).

## Is Engine 2.x running Kosmos?

Yes. Kosmos has consumed the TypeScript Engine as the pinned `gkos-engine`
package since 0.8.0, and 0.8.3 already pinned a 2.2.0 commit. The plugin view,
the standalone viewer and the Agent API all build their graph through the
Engine (`GkxIndex`/`buildGraph`, GKX 2.3 projection, `projectAtTime`, Graphiti
export, Navigation and Navigation Effects contracts). What had drifted was the
pin: Engine `main` was 86 commits ahead.

The way to keep Kosmos's UI and behaviour while following the Engine's intent
is the existing split, kept strict: Engine owns semantics (parsing, projection,
policy, lineage, retrieval), Kosmos owns presentation and transport, and Kosmos
moves to newer Engine commits by exact pin rather than copying logic. This
release follows that rule:

- The increment `777ba17..7511233` only adds exports. Every root, `adapter`,
  `navigation` and `navigation-effects` export Kosmos uses is unchanged, and
  `src/` type-checks against both commits.
- `get_lineage` now carries Engine-resolved authored declarations
  (`inspectScopedLineage`) instead of Kosmos re-deriving them. Hidden targets
  report `unresolved` with no identity, which matches the Agent API's
  sensitivity ceiling.
- Not adopted, and why: `./governance/artifacts` (GKX 2.0 validator, context
  assembly, reviewer v2) and `./retrieval` sessions are Node-only (`node:crypto`,
  `node:sqlite`), so they cannot run in the renderer or on mobile. Clearance-bound
  Graphiti search and lexical discovery live in the Engine's own service, outside
  its exports map. Using any of them needs an Engine-side export or a desktop-only
  path, which is an owner decision.

Two new tests in `test/agent-lineage-declarations.test.mjs` cover a resolved
declaration and an unreadable target that must not leak. They load the agent
server and `buildGraph` from one bundle (`dist/kosmos-agent-lineage-test.mjs`)
because the Engine keys its lineage ledger by graph identity; a graph built by
the separately bundled `dist/kosmos-core.mjs` carries no ledger. The plugin's
`main.js` is a single bundle and is unaffected.

## Renderer measurements

Chromium (Playwright, `--use-angle=d3d11`), Intel UHD Graphics, 1600x900,
overview with auto-rotate, synthetic vaults built with `kosmos-build.mjs`,
8-second windows, CDP `ScriptDuration` per frame:

| Vault | 0.8.3 (`main`) | 0.8.4 |
| --- | --- | --- |
| 3,000 notes | 60 fps; 1.36-1.41 ms script/frame | 56-60 fps; 1.23-1.33 ms |
| 15,000 notes | 26.6-28.5 fps; 5.6-5.8 ms | 60 fps; 2.8-3.1 ms |

Most of the 15,000-note gain comes from no longer painting the hidden minimap
(one 2D arc and fill per note every fourth frame). Rendering every other frame
at idle overview, the existing behaviour, still applies. These are single-machine
measurements, not hardware-independent budgets.

## Not established

This does not establish an Engine release, GKOS conformance, native Obsidian or
Hermes acceptance of 0.8.4, or Graphiti promotion. Open 0.8.3 gates in
[REVIEW-0.8.3](../REVIEW-0.8.3.md) remain open. To roll back, restore the
previous package, lock, guard and fixture coordinates together, rebuild and
rerun verification.
